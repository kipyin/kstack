# define-golden-cases

**目的**：协助业务人员为特定功能确定 golden cases，即实现之前锁定的验收数值。Agent 负责推导与复核，业务人员负责确认。

**骨架**：场景清单 → 业务确认 → 逐个 case 确立 golden values → 业务逐个确认 → 记录口径。

**golden 的定义**（贯穿全流程）
- **预期值独立确认**：来自监管要求、第一性原理、不变量或业务人员确认；在实现之前确定，不由实现代码自行计算。已有实现但行为错误时，case 失败即需修复 spec。
- **容差匹配数值量级**：大数值用相对误差，接近零的数值用绝对误差兜底，比率与因子收紧容差。
- **边界**：测试文件落入 `tests/golden/` 并通过，属于实现阶段的任务；本 skill 只定到 spec。

## 第一轮：场景清单 → 业务确认

1. **锚定口径**：从监管文件、wayfinder map、spec 提取口径；现有代码（如有）仅用于理解差距。
   - 完成条件：每个待测行为都能说明监管或业务依据。
2. **列举场景**：用通俗易懂的语言列出待测场景，按「出错影响 × 出错概率」排序。
   - 完成条件：场景已排序，每个场景可一句话概括。
3. **标注归属**：每个场景标注「监管确定」或「实现选择」（监管未规定、留给实现层决定的细节）；「实现选择」的口径请业务人员裁定。
   - 完成条件：每个场景都有归属，「实现选择」口径均已裁定。
4. **业务确认场景清单**：场景清单连同「实现选择」口径，交业务人员确认。

## 第二轮：逐个 case 确立 golden values → 业务逐个确认（按风险优先级）

5. **独立推导 expected**：通过解析求解、手算、第一性原理或不变量推导。
   - 完成条件：每个 expected 都有可追溯的独立推导来源。
6. **确定断言粒度（testing seam）**：选取能表达业务真相的最粗粒度层级，通常是传递给下游的业务输出（监管确定、唯一、与实现无关）；更细的内部拆分仅在监管确定且解唯一时才锁定。
   - 完成条件：每个 case 标注断言层级。
7. **双重独立复核**：用第二种独立方法复核每个 expected（更换推导路径，或编写另一段独立计算逻辑）。
   - 完成条件：每个 expected 经第二种方法复核一致。
8. **展示推导过程并确认**：向业务人员展示推导过程与结果，而非只给数字；expected 可以是具体数值，也可以是不变量（守恒、顺序无关、该功能特有的）。
   - 完成条件：业务人员逐个确认 golden values。

## 收尾：记录口径

9. **归档口径**：「实现选择」的口径写入 spec/agent brief，case 引用相关口径；ADR 留待实现阶段。
   - 完成条件：每个 case 的口径已写入 spec/agent brief，或确认为监管要求。

**产出**：一组 golden cases（场景、业务确认的 golden values、容差），以及写入 spec/agent brief 的口径决定；作为 spec/plan 的一部分，在实现之前确定。
