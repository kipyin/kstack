# Gitee PR Address (resolve reviews on your own PR)

Use this skill to **address** review comments on a Gitee PR you own. It is the
counterpart to `gitee-pr-review` (which writes reviews on others' PRs) and
`gitee-pr-workflow` (which lands). Review-address only: do not approve, merge,
or close here.

The reviewer is not the spec. The user asked: check whether each point is a
**real** problem before doing anything. Re-validate every item against the
code and diff yourself; the review's own section headers (`需要决策` /
`机械性问题` / `建议` / `范围之外`) are a reading aid, not a verdict.

## Prerequisites

- `gitee` Rust CLI on `PATH`, authenticated once. **Always pass `--remote gitee`**
  (this repo has no `origin`).
- The PR number from the user, or a branch they name (resolve to number via
  `gitee pr list --remote gitee --state open --json number,title,head`).
- A local checkout of the PR branch: `gitee pr checkout <N> --remote gitee`,
  or be on the PR branch already. Fixes commit here, on the PR branch.

## Triage loop (run in order; complete before replying)

1. **Fetch.** General comments via the CLI:
   `gitee pr comment list <N> --remote gitee --type general --json` (works).
   Diff/inline comments via `--type diff` can hit the `position` decode bug
   (see `gitee-pr-review` Pitfall #3); if it errors, fall back to curl:
   `curl -s "https://gitee.com/api/v5/repos/hrcblazers/lighthouse/pulls/<N>/comments?access_token=$TOK&per_page=100"`
   where `TOK=$(find "$HOME/Library/Application Support/gitee" -name '*.token' -exec cat {} \;)`.
   Filter out your own comments (`user.login` == current user, from `gitee api user`)
   and any `> *This ... was generated by AI during triage.*` reply you already
   posted. What remains is open review input.
   - Completion: you have a list of review items to address, each tied to a
     comment id and the file:line it points at.

2. **Re-validate.** For each item, open the cited code and the PR diff
  (`gitee pr diff <N> --remote gitee`). Confirm the cited line exists, says what
  the review claims, and the claimed consequence holds. Read the linked issue
  / spec if the item is spec-shaped. Decide the disposition independently.
   - Completion: every item carries one disposition and a one-line **why**,
     grounded in the code, not the review's wording.

3. **Act per disposition** (below). Mechanical fixes first, in dependency
  order; decisions and pushbacks queue for the user.
   - Completion: every `fix` item is fixed at root with a runnable check
     passing; every `confirm` and `pushback` item has a plain-language block
     ready for the user.

4. **Reply** (below), one consolidated comment. Then report to the user here.
   - Completion: the PR has one new comment covering every item; the user sees
     a short summary of fixes, decisions needed, and pushbacks.

## Dispositions (three; reuse the review's words when they fit)

- **fix** - mechanical. A real defect with an obvious correct fix: a missing
  timeout, an over-broad `except`, a banned em dash, a wrong type, a broken
  test assertion. Fix it. Do not ask.
- **confirm** - real, but the resolution forks: a naming choice, a scope
  boundary, an accepted risk window, a behavior change. You cannot pick for
  the user. Pause and ask.
- **pushback** - not a real problem, or the premise is wrong, or it is already
  handled and the reviewer missed it. Do not change code to appease it. Explain.

Items the review filed as `建议` or `范围之外` are usually `pushback` or
`confirm`; they are rarely `fix`. Items it filed as `机械性问题` still need
re-validation before they earn `fix`.

## fix - greenfield, not patch-on-patch

A review comment is usually a symptom. Fix the root, once, in the shared
place, not at the call site the reviewer happened to read. Follow the ponytail
ladder in `AGENTS.md`: grep every caller of the function you touch; encode the
invariant earlier (type, schema, single validation gate) if the same class
recurs; prefer earlier failure.

Think from **greenfield**: read the area as if writing it fresh, find the
shape that makes this defect impossible, then move toward it with the smallest
diff. Do not stack a guard on top of the broken code to silence the comment.

Leave **one runnable check** behind for non-trivial logic (assert-based
self-check or one small test file; no frameworks, no fixtures). Trivial
one-liners need no test. Re-run the touched suite before committing.

Commit on the PR branch and `git push` to the PR's remote branch so the PR
updates. Do not merge.

## confirm - plain language, with options

When you hit a `confirm`, stop and ask the user here. Do not silently pick.
Describe in plain language, no jargon dump:

- the point the review raised, in one or two sentences;
- why it is a real fork (what changes depending on the answer);
- the concrete options, each with its cost or risk;
- your recommendation and the one reason for it.

If the review is in Chinese, reply to the user in Chinese. Wait for the answer
before touching code for that item.

## pushback - plain language, with evidence

When a comment is unreasonable, tell the user so and why, and reply on the PR
with the same reasoning. Ground every pushback in the code or the spec, not
opinion. Forms it takes:

- **premise wrong**: the cited line does not say / do what the review claims;
  quote the line.
- **already handled**: a test, an earlier commit, or an out-of-scope note
  already covers it; point at it.
- **out of scope**: the change belongs to another issue; name the issue and
  link it.
- **style without force**: e.g. a naming preference with no contract behind it;
  say so plainly.

If after re-validation you are unsure whether something is real, treat it as
`confirm` and ask, do not silently `fix` or `pushback`.

## Reply (one consolidated comment)

Inline/diff line comments are broken in this toolchain (see `gitee-pr-review`
Pitfalls). Post **one** PR-level comment via
`gitee pr comment create <N> --remote gitee --body "$(cat <<'EOF' ... EOF)"`,
grouped:

```markdown
> *Generated during gitee-pr-address.*

### 已修复（机械性，本轮提交 <sha>）
- **<point>**：<what was wrong> -> <root fix>, one line. <check added>.

### 需要你定（已暂停，未改）
- **<point>**：<plain-language problem>. 选项：
  1. <option A> - <cost>
  2. <option B> - <cost>
  建议：<pick>，因为：<one reason>.

### 不采纳（附依据）
- **<point>**：不采纳，因为 <premise wrong | already handled at <ref> | out of scope, see <issue>>.
```

Use `--preview` first; only post after the user has decided any `confirm`
items that affect the reply's content. Keep each line to the decision, not a
re-explanation of the review.

## Boundaries

- Do not approve, merge, or close. Landing is `gitee-pr-workflow`.
- Do not rewrite code outside the cited defect's root just because the review
  wandered. Park scope creep as `pushback` (out of scope) with the issue link.
- Do not edit the reviewer's comment or delete it; reply.

## Pitfalls

- Trusting the review's own `机械性问题` label without reading the code. That
  label has been wrong before. Re-validate.
- Patching the cited line to make the comment go quiet while the shared
  function stays broken for sibling callers. Fix the shared function once.
- Asking about a `confirm` in code jargon. Translate to the user's language
  and the user's stakes.
- Replying per-comment. Gitee inline/diff comments are unreliable here; one
  consolidated PR-level comment.
- `gitee pr comment list --type diff` may throw `error decoding response body`
  (the `position` int/String bug). Use `--type general` for the CLI; for diff
  comments use the curl fallback in step 1, not a blind CLI retry.
- A `comment create` decode error can still mean the POST succeeded. Read back
  before retrying; a blind retry double-posts. Clean up any stray/duplicate
  via the curl DELETE in `gitee-pr-review` Pitfall #3.
- Forgetting to push the fix commits. A fix not pushed to the PR branch is
  not addressed; the reviewer still sees the old code.
