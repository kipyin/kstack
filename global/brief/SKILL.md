# brief

给 Kip 的状态必须让他一眼知道**找谁、下一步做什么**。裸 issue 编号不算状态。

## 什么时候用

发以下任何东西之前，先读这个 skill：

- 工作清单、优先级清单、进度总结
- 「在等什么」「卡在哪」「本周要事」
- 偏离提醒里附带的等待项

## 每一行的形状

缺一不可：

1. **短标题** — 人话一句说清这件事是什么（可附 `repo#n` 定位，但不能只有编号）
2. **负责人** — 现在谁在收尾（伙伴名或人名）
3. **Kip 的下一步** — 他要做什么，或明确「不用动 / 等 X」

好例子：

- `lightmind 等待托盘：Vera 收尾 → 你点 OK 效果图即可`
- `245 部署：等 Andrew 修好凭据 → 你暂时不用动`
- `PwC 材料包：Doris 整理中 → 周五会前你过一眼大纲`

禁止：

- `#790`
- `lightmind#518 进行中`
- `若干 PR 待验收`

## 核实纪律（Kip 2026-10-23）

凡是写「已完成 / 已落地 / 还在做」：

- **禁止凭记忆**
- **禁止只看 issue 留言**
- **必须**去代码库和/或数据库（含 245）取证据

对不上就标「未确认」或「证据不足」，不要装成已知。owner 的对话只能用来找人、对齐下一步，不能单独当落地证据。

## 发出前

1. 对每个 owner 拿**实时**进展（问本人，或读最近对话），不要发过时快照
2. 状态结论按上面核实过
3. 未确认的标「未确认」
4. 用 Kip 跟你说话的语言（通常是中文）；repo、issue id、命令、链接保持英文原样
5. 短。不要倒豆子，他要细节再展开

**Done when**：每一行都能回答「是什么 / 找谁 / 我下一步做什么」，没有裸编号行，状态结论有代码库或 DB 证据。

## 笔记与动作分开

- **动作**（清单 / Project）：动词 + 对象 + 期限
- **笔记**（长期笔记本）：交接、会议决定、邮件摘要、持久背景

不要把散文写进动作清单，也不要把看板快照倒进笔记。长对话先 `/handoff` 压缩，再把结论落进笔记本。细节在别处就用 URL 链出去，别复制进来。

笔记不擅自用产品绰号或 bot 名字命名，除非 Kip 已经这么叫了。
